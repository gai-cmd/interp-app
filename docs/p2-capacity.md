# P2 규모 시험과 운영 판정

기준: `design-p2.md` §8.5·8.6·9·10·17 및 P2-22. P2-21의 통합·개인정보 회귀를 전제로 한다. 이 문서는 오프라인 도구와 현장 기록 틀이다. 목표 규모·실기기 성능·행사장 합격은 **미확정·미검증**이다. 기존 P1 검수 기록은 `p1-20b-review.md`, `device-matrix.md`, `venue-runbook.md`에 유지한다.

## 1. 오너가 확정할 운영 입력

| 입력 | 확정값 | 근거·확정일 |
|---|---|---|
| `N_max` 최대 동시 청중 | 미확정 | |
| `N_direct` / `N_hub` | 미확정 | 합계가 N_max와 일치해야 함 |
| `L_active` 실제 동시 방송 언어 수 | 미확정 | |
| `N_by_language` 경로별·언어별 인원 | 미확정 | 언어별 합계와 경로별 합계 확인 |
| `T_service_minutes` 전체 예배 길이 | 미확정 | |
| `D_caption_p95_max` 실제 자막 지연 허용치 | 미확정 | 측정 시작·끝 정의 포함 |
| `D_audio_p95_max` 실제 음성 지연 허용치 | 미확정 | 물리적 첫소리 기준 |
| `E_max` / `G_max` 실패율·누락 허용 기준 | 미확정 | 분모와 판정 단위 명시 |

입력 미확정이면 목표 규모 합격을 내리지 않는다. 정원·언어 분포·전체 길이를 변경하면 해당 조건으로 다시 시험한다.

## 2. 오프라인 명령

저장소 루트, Node 24, 외부 npm 패키지·빌드·키·방 코드가 필요 없다.

```sh
node scripts/p2-load.mjs --mode mock --listeners 4 --languages 2 --duration-seconds 10
node --test tests/p2-load.test.mjs
node --test tests/*.test.mjs
node --test tests/
node scripts/check-i18n.mjs
git diff --check
```

4·2·10은 재현용 작은 사례이며 목표 인원·목표 언어·목표 시간이 아니다. `--mode`를 생략해도 mock이며 실서버 모드는 없다. N/L/T 옵션은 모두 필수다. 부호·소수·지수 표기 없이 양의 안전 정수만 받고, 중복·알 수 없는 옵션·누락·산술 오버플로를 거부한다. L은 기존 앱 프로토콜의 ko/en/ja에 맞춰 1~3이며, 초과값을 3으로 조용히 자르지 않는다. N과 T에는 임의의 운영 목표나 기본값이 없다. 매우 큰 입력은 로컬 CPU·메모리를 소모하므로 작은 사례부터 늘린다.

출력은 집계 JSON, 성공 종료 코드는 0이다. 잘못된 인자는 `P2_LOAD_INVALID_ARGUMENTS`, 실행·불변식 실패는 `P2_LOAD_FAILED`와 종료 코드 1이다. 인자 원문·예외 스택은 출력하지 않는다. `--room`, `--key`, URL 옵션은 지원하지 않으며 실제 비밀을 명령행에 넣지 않는다. UI를 추가하지 않았으므로 JSON 필드와 오류 코드는 기계용 계약이며 브라우저 표시 문구가 아니다.

## 3. 생성·검사 범위

도구는 새로 작성한 메모리 소켓·가상 시계·모의 기기 음성에 기존 `app/hub/client.js`, `app/engine/caption-store.js`, `app/audio/caption-speaker.js`를 연결한다. 원본 translate/live/xlsx·주입 스크립트를 새로 이식하지 않는다. 제공자 라우터·키·마이크·실제 네트워크는 호출하지 않는다. 코드 내 `.invalid` 주소와 고정 모의 참가 값은 클라이언트 검증을 통과시키기 위한 가짜 입력이고 출력에 남지 않는다.

- N개 독립 청중은 언어를 순환 배정한다. L>N도 가능하며 청중이 선택하지 않은 언어까지 모두 수신·정렬한 후 음성 언어를 고른다.
- 가상 1초마다 언어당 4개 구간을 생성한다. 각 구간은 partial, final, 같은 final 중복, 높은 revision의 final 수정 순서다. 트래픽 생성률은 재현용 시험 조건이다.
- 번역문은 합성 식별용 텍스트다. 전송은 모든 언어가 공유하는 seq 순서를 유지한다. 자막은 snapshot으로 갱신하고 수정·중복 final을 다시 읽지 않는다.
- 짝수 인덱스 청중은 문장당 5초, 나머지는 50ms에 끝나는 모의 TTS를 사용한다. 기다리는 큐 20개, 오래된 대기 생략, 단일 재생을 검사한다. 실제 TTS watchdog·음성 품질은 현장 시험 대상이다.
- T초 생성 후 모든 청중을 한 번 재접속한다. 느린 청중의 Blob 해석을 보류해 실제 수신 큐의 개수·바이트 상한을 번갈아 넘긴다. N=4 사례는 두 종류 모두 시험한다. 다른 청중은 정상 단절을 모의한다.
- 이전 소켓 종료 뒤 가상 1초 재시도로 hello와 전체 언어 합산 최근 final 최대 30개를 전달한다. 이미 본 final은 억제하고 전 청중을 음소거해 replay를 자동 낭독하지 않는다. 단절은 누락 가능으로 표시한다. 실제 서버에는 replay 경계·안정적인 방송 ID가 없으므로 이 합성 경계를 제품의 판별 능력으로 해석하지 않는다.
- 수신 최대 128개·2MiB, 메시지당 1MiB는 기존 클라이언트 상수를 사용한다. 확정·중단 자막 100개와 활성 partial, 중복 ID 부재, TTS 대기 20개, 재접속·순서·중복 낭독 0, 종료 후 관측 가능한 자원 0을 검사한다.

가상 T초는 실제 대기 시간이 아니다. `virtualElapsedMs`에는 별도의 재접속 1초가 추가된다. mock 통과는 실제 AP·허브 송신 부하, 직접 Live 입력/PCM 처리, 제공자 한도, DOM, 배터리, 실제 종단 지연을 검증하지 않는다. 해당 자동 회귀는 전체 테스트로, 실제 동작은 P2-23·24로 분리한다.

## 4. 메모리 수치의 의미와 제한

| 출력 | 의미 |
|---|---|
| `maxTrackedRecords` | 최근 final + 청중별 현재 자막 행·수신 대기·TTS 대기·활성 발화·파생 ID 항목 수의 관측 최대 합계 |
| `identityEntriesDerived` | 선택 언어의 고유 final 입력으로 계산한 TTS 재낭독 방지 ID 항목 수 |
| `maxCaptionRows` | 한 청중의 자막 행 최대값. partial 때문에 100을 넘을 수 있음 |
| `finalTrackedRecords` | 종료 후 관측 가능한 자막·큐·활성 발화·소켓·타이머 합계. 0이어야 함 |
| `heapBeforeBytes` / `heapAfterBytes` | Node 프로세스 heapUsed. GC 시점·테스트 실행 환경에 따라 변동 |
| `exactHeapObjectCount: null` | VM 전체 객체 수는 측정하지 않음 |

관측 합계는 `30 + N × (100 + L + 128 + 20 + 1 + 4×T)` 상한과 대조한다. 이는 시험 입력에 따른 레코드 수 상한이며 일정 메모리를 보장하는 운영 기준이 아니다.

항목 수는 전수 힙 객체 수나 바이트 수가 아니다. 공유 객체를 여러 항목으로 셀 수 있고 내부 클로저·Promise·문자열·Map·스냅샷 복사 등은 전수 집계하지 않는다. 마지막 0도 GC 완료·메모리 누수 부재 증명이 아니다.

현재 TTS `seen`은 참가 epoch 종료까지 ID를 보관한다. 이 도구의 입력에서는 청중별 4×T 항목, 총 N×4×T 항목으로 증가한다. 텍스트 큐가 제한돼도 ID 메모리는 시간에 비례한다. 내부 Set은 공개 조회 인터페이스가 없어 입력으로 유도한 수이며 실제 힙 계수로 표시하지 않는다. P2-22에서는 다른 과제의 구현을 바꾸지 않는다. P2-24에서 목표 전체 길이의 브라우저·허브 메모리 추이를 별도 확인하고, 증가가 운영 기준에 맞지 않으면 운영 보류 또는 별도 구현 과제로 넘긴다.

## 5. 현 서버 제약

로컬 원본 `~/jarvis2/interp-web/server.js`와 `lib/live.js`, `design-p2.md` §10 기준(2026-09-06 소스 확인). 실제 행사 배포 서버 버전은 현장에서 별도 기록한다.

| 제약 | 운영 영향 |
|---|---|
| 방송 언어 목록 최대 3개로 절단 | L_active>3 요구는 현재 서버로 합격 불가 |
| 방송 시작 후 150분 자동 종료 | 목표 전체 길이·준비 방송 시간을 포함해 대조. 150분 초과 무중단 운영 합격 불가 |
| 느린 청중에 대한 명시적 송신 버퍼 상한 없음 | 클라이언트 수신 제한으로 서버 메모리 안전을 주장할 수 없음 |
| 청중에 생성 PCM을 보내지 않음 | 실제 음성은 청중 기기의 TTS이며 지원 음성·지연을 따로 검증 |

위 수치는 운영 목표가 아니다. 초과 요구는 정원·시간·재참가 절차 조정 또는 해당 운영 보류로 처리한다. 중간 방송 재시작은 무중단 시험 통과가 아니며, 새 참가·음성 수동 재개와 실제 누락을 기록한다.

## 6. 실제 시험 절차와 기록표

1. 오너가 §1 입력과 중단 기준을 작성한다. 앱 릴리스, 서버 리비전, 제공자·모델, 기기·OS·브라우저, AP 모델·펌웨어·주파수·배치, 회선과 경로별 인원·언어 분포를 기록한다. 키·방 코드·인증 URL은 제외한다.
2. 등록된 HTTPS/WSS, DNS, 게스트 Wi-Fi 접근을 실제 청중 기기에서 확인한다. 허브 경로는 마이크·청중 API 키 없이 참가한다. 공용 직접 경로는 기존 런북의 내부 허용·외부 거부·이동·폐기 시험을 별도로 통과해야 한다.
3. 10분 예비 시험을 수행한다. 실제 청중 기기를 점진적으로 늘리고 동일 조건의 안정 구간과 느린 기기·회선 단절·재접속·AP 이동·백그라운드/복귀 구간을 구분한다. 운영 중 사용자에게 영향을 주는 시험은 격리된 리허설에서 수행한다.
4. 예비 결과 후 확정한 N_max·언어 분포·전체 T_service_minutes로 실제 전체 길이 시험을 수행한다. 모의 프로세스 N개는 실제 Wi-Fi 기기 N개를 대체하지 않는다. 직접·허브 동시 사용 조건도 포함한다.
5. 허브 CPU·RSS/heap·LAN 송수신량, 클라이언트별 송신 대기(계측 가능 시), AP 연결 수·재전송·채널 사용량, 앱 큐·복구·오류·누락을 같은 경과 시간축으로 기록한다. 느린 청중이 다른 청중과 서버 메모리에 미치는 영향을 확인한다. 계측 불가 항목은 미지원/미측정이며 0으로 채우지 않는다.
6. 허가된 합성 시험 발화로 발화 시작→실제 첫 자막 표시/이어폰 첫소리를 외부 관측한다. 앱 단조 시계·AudioContext 예약·TTS 요청은 내부 지표로 별도 기록한다. 서버 ts와 폰 시각은 동기화 검증 없이 빼지 않는다. 표본 수·관측 실패 수·p50/p95/최대를 남기고 정확도·누락·첨가를 평가한다. 기본 결과에는 발화·번역·오디오를 저장하지 않는다.
7. 중단·방송 종료·기기 복귀·재참가·키 폐기 후 자원 정리를 확인하고 장애 조치와 허용 운영 범위를 연결해 판정한다. 시험 중 목표·임계치를 바꾸면 별도 회차로 기록한다.

## 7. P2-22 구현 결정

신규 파일은 `scripts/p2-load.mjs`, `tests/p2-load.test.mjs`, 이 문서이며, 기존 `venue-runbook.md`와 `device-matrix.md`는 P1 기록을 유지하고 P2 절을 추가했다. 기존 테스트 단언은 변경하지 않았다. 설계 계약 변경은 없다. T는 정수 초, 언어는 앱 지원 3개 이내로 검증하며 실서버 자동 부하 모드는 제공하지 않는다. 메모리 전수 계수 대신 공개 상태의 항목 수와 ID 증가 추정치를 구분해 보고한다. 외부 패키지·앱 파일·제공자 계약 변경은 없다.
