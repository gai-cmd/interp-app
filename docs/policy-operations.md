# 정책 운영 절차 (P3-33)

관리자 콘솔은 **정책 파일을 만드는 도구**다. 발행은 사람이 저장소에 반영하는 행위이며,
콘솔에는 배포 호출이 없다. 이 문서는 그 경계와 절차를 적는다.

기준: [design-p3.md](design-p3.md) §1.5·§1.7·§1.15, [architecture.md](architecture.md).

## 1. 콘솔이 하는 일과 하지 않는 일

| 하는 일 | 하지 않는 일 |
|---|---|
| 배포된 `policy.json`을 읽어 비교 대상으로 삼음 | 편집 중인 초안을 **실행 중인 앱에 적용** |
| 앱과 **같은 validator**로 검사(`app/policy/schema.js`) | 별도의 느슨한 관리자용 파서 사용 |
| 변경 미리보기(중지·기능·잠금·revision) | 배포·발행 API 호출 |
| JSON 다운로드·복사·수동 복사 fallback | "발행 완료" 표시 |
| 행사 공용 키 payload 생성(정책과 분리) | 정책 JSON에 키 포함 |

콘솔은 `localStorage`·`sessionStorage`를 쓰지 않고, 앱의 키 저장소를 읽지 않는다.
회귀 테스트(`tests/admin-editor.test.mjs`, `tests/privacy.test.mjs`)가 이를 소스 대조로 단언한다.

## 2. 발행 절차

1. 콘솔에서 편집하고 **검증을 통과**시킨다. 검증 실패 시 내보내기 자체가 막힌다.
2. **revision을 올린다.** 내용이 달라졌는데 현재 배포된 revision을 그대로 쓰면 내보내기가 거부된다.
3. JSON을 다운로드하거나 복사한다. **이 시점은 발행이 아니다.**
4. 저장소의 배포 루트 `policy.json`을 새 내용으로 교체한다.
5. 코드 검토 후 커밋하고 배포한다. **발행 권한은 저장소·배포 권한이다.**
6. 앱에서 정책을 다시 불러와 **revision이 바뀌었는지 확인**한다. 이 확인이 유일한 발행 증거다.

## 3. 캐시와 롤백 (P3-35)

- `policy.json`은 배포 루트에 있지만 **셸 캐시에 넣지 않는다.** 서비스워커의 shell 목록에서 제외되고,
  `_headers`는 `no-store`를 준다. 앱도 요청 측에서 `no-store`로 조회한다.
- `admin/index.html`도 캐시하지 않는다(`no-cache`). 캐시된 콘솔은 이미 바뀐 정책을 보여준다.
- **롤백(`stage-release --point`)은 정책을 덮지 않는다.** 이전 빌드에 딸려 있던 정책을 되돌리면
  긴급 중지나 기능 변경이 조용히 풀린다. 롤백은 진입 파일만 이전 릴리스로 되돌린다.
- 정적 CDN 갱신·오프라인·백그라운드 때문에 **모든 기기에 즉시 반영되지는 않는다.**

## 4. 되돌리기

정책을 되돌릴 때 **revision을 낮추지 않는다.** 이전 내용으로 **새 revision을 발행**한다.
앱은 더 낮은 revision을 옛 정보로 취급하도록 만들어져 있고, 번호를 되돌리면 그 판단이 깨진다.

## 5. 공용 키 payload

- 정책 편집과 **분리된 도구**다. 키는 메모리에만 있고 닫기·이탈 시 지워진다.
- 생성 결과는 링크 길이와 메타데이터만 돌려주며 **키를 되돌려주지 않는다.** 키는 복사할 때만 이동한다.
- 활성·미만료·활성화된 행사만 지정할 수 있고, 제공자·행사명·만료는 배포된 정책에서 가져온다.
- 생성한 링크는 **앱의 파서로 왕복 검증**한 뒤에만 제공한다.
- QR의 행사 ID는 서명이 아니며 관리자 신원을 증명하지 않는다. 실제 키 폐기는 제공자 콘솔에서 한다.
